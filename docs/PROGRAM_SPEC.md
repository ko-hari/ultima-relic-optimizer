## 6. 확률 모델

현재 모델에서는 남아 있는 모든 미확인 셀이 동일한 보상 확률을 가진다고 가정한다.

미확인 셀 수를 `N`, 남은 보상 수를 `R`이라고 하면 개별 셀의 보상 확률은 다음과 같다.

```text
P(셀의 보상) = R / N
```

후보 아이템이 `n`개의 미확인 셀에 영향을 주는 경우 다음 값을 계산한다.

### 6.1 기대 신규 보상

```text
기대 신규 보상 = n × R / N × 아이템 배수


```

일반 아이템의 배수는 `1`이고 Special Boom은 `2`를 사용한다.

### 6.2 보상 한 개 이상 발견 확률

```text
1 - C(N-R, n) / C(N, n)
```

이는 선택된 효과 범위 안에서 보상을 최소 한 개 이상 발견할 확률이다.

### 6.3 완료 확률

남아 있는 모든 보상이 해당 아이템 효과 범위 안에 들어갈 확률이다.

```text
C(n, R) / C(N, R)
```

단,

```text
n >= R
```

인 경우에만 0보다 큰 값을 가질 수 있다.

## 8. 추천 알고리즘

### 8.1 Analytical

기본 추천 방식이다.

1. 수량이 1개 이상인 수동 아이템만 선택한다.
2. 아이템별 유효 표적을 생성한다.
3. 공개된 셀을 제외한 실제 효과 셀 집합을 계산한다.
4. 기대 보상을 계산한다.
5. 신규 탐색 셀 수를 계산한다.
6. 보상 한 개 이상 발견 확률을 계산한다.
7. 완료 확률을 계산한다.
8. 사용자가 선택한 목표 함수에 따라 점수를 계산한다.
9. 목표 함수 점수 기준으로 내림차순 정렬한다.
10. 점수가 같으면 기대 보상과 탐색 셀 수를 추가 정렬 기준으로 사용한다.
11. 상위 5개의 추천을 반환한다.

분석적 방식은 가능한 후보를 직접 계산하기 때문에 기본 추천 결과로 사용한다.

### 8.2 Monte Carlo

Monte Carlo 방식은 분석적 결과를 확률적 시뮬레이션으로 검증하기 위한 기능이다.

처리 과정은 다음과 같다.

1. 분석적 평가를 먼저 실행한다.
2. 상위 후보를 시뮬레이션 대상으로 선택한다.
3. 남은 보상 `R`개를 `N`개의 미확인 셀에 균등하게 무작위 배치한다.
4. 후보 아이템 효과를 적용한다.
5. 실제 발견 보상 수를 기록한다.
6. 지정된 횟수만큼 반복한다.
7. 평균 발견 보상과 확률을 계산한다.

기본 seed는 다음과 같다.

```text
42
```

웹 인터페이스의 기본 반복 횟수는 다음과 같다.

```text
1,000회
```

Monte Carlo 결과는 확률 및 기대값 검증에 사용하며 후보의 기본 정렬 점수는 분석적 점수를 사용한다.

## 10. 보드 크기 자동 판별

보드 크기는 기본적으로 격자 경계의 주기성을 이용하여 판별한다.

후보 크기는 다음 세 가지다.

```text
5×5
10×10
15×15
```

각 후보 크기로 보드를 분할했을 때 격자선 위치와 실제 이미지 경계가 얼마나 잘 일치하는지를 점수화한다.




### 10.1 색상 아이템 기반 보정

격자선만 이용할 경우 보드 후반부처럼 공개된 셀이 많아졌을 때 실제보다 작은 보드로 인식할 가능성이 있다.

이를 보완하기 위해 각 후보 크기로 보드를 임시 분할한 후 색상 보상 및 아이템이 포함된 셀 수를 계산한다.





* 5×5 후보에서 색상 아이템 셀이 9개를 초과하면 후보에서 제외한다.
* 10×10 후보에서 색상 아이템 셀이 36개를 초과하면 후보에서 제외한다.
* 15×15는 현재 지원하는 최대 크기이므로 최종 폴백 후보로 유지한다.

실제 고정 보상 수는 각각 8개와 32개지만 아이콘이 셀 경계에 걸쳐 인접 셀에서도 검출될 수 있으므로 일정한 여유를 둔다.






### 10.2 아이콘 배치 주기 보정

색상 아이콘 픽셀의 2차원 배치 역시 보드 크기 판단에 활용한다.










각 색상 픽셀에서 다음 후보 격자의 셀 중심까지의 정규화 거리를 계산한다.

```text
5×5
10×10
15×15
```

평균 거리가 작을수록 해당 격자 구조에 잘 정렬되어 있다고 판단한다.




다음 조건을 만족할 때만 이 신호를 사용한다.

* 색상 픽셀이 보드 가로 방향의 30% 이상에 분포
* 색상 픽셀이 보드 세로 방향의 30% 이상에 분포
* 특정 후보의 중심 정렬 오차가 충분히 작음
* 다른 후보보다 오차가 명확하게 낮음

아이콘이 적거나 여러 격자 크기에 동시에 잘 맞는 경우에는 아이콘 배치만으로 보드 크기를 결정하지 않는다.




복수 후보가 비슷하게 정렬되면 프레임 경계와 격자선 주기성 결과를 우선하고 조건을 만족하는 최대 후보 크기를 선택한다.


이미지가 전달되지 않은 경우 기본 샘플 이미지인 `Sample_Board.png`를 분석할 수 있다.

응답에는 다음 정보가 포함된다.

* 보드 크기
* 셀 상태
* 고정 총 보상 수
* 발견된 보상 수
* 남은 보상 수
* 인식된 아이템 수량
* 보드 영역 좌표
* 원본 이미지 정보

### 11.3 `POST /api/recommend`

분석된 보드 상태와 아이템 수량을 받아 추천을 수행한다.

```text
Content-Type: application/json
```

주요 입력:

```text
board
inventory
objective
mode
iterations
```

`mode`는 다음 두 가지를 지원한다.

```text
analytical
monte_carlo


```

추천은 가장 높은 점수 순으로 최대 5개를 반환한다.

API 좌표는 0부터 시작한다.

### 11.4 오류 코드



| HTTP 상태 | 의미                     |
| ------: | ---------------------- |
|     200 | 성공                     |
|     400 | 보드 크기, 셀 상태 또는 입력 값 오류 |
|     413 | 업로드 제한 초과              |
|     500 | 처리되지 않은 서버 오류          |

웹 GUI는 사용자가 프로그램 내부 구조를 알지 않아도 스크린샷만으로 분석과 추천을 수행할 수 있도록 구성한다.

### 12.1 클립보드 이미지 입력

페이지 어디에서나 다음 입력을 사용할 수 있다.

```text
Ctrl + V








```

클립보드에 이미지가 존재하면 이를 즉시 분석 대상으로 사용한다.

일반 텍스트 붙여넣기는 가로채지 않는다.

### 12.2 아이템 수량 표시

하단 슬롯에서 자동 인식한 아이템 수량을 다음 형태로 표시한다.

```text
Boom ×1
Special Boom ×0
Lazer X ×2
Lazer Y ×1
```

수량은 이미지 분석 결과이므로 기본적으로 읽기 전용으로 표시한다.

### 12.3 추천 Top-5

추천 결과는 높은 점수 순으로 최대 5개 카드로 표시한다.

각 카드에는 다음 정보가 포함될 수 있다.

* 추천 순위
* 아이템 이름
* 표적 좌표
* 신규 탐색 셀 수
* 기대 보상
* 보상 한 개 이상 발견 확률
* 완료 확률
* 종합 점수

### 12.4 이미지 오버레이

원본 이미지 위에 추천된 아이템의 효과 범위와 실제 표적을 표시한다.

표시 규칙:

* 반투명 빨간 셀 → 아이템 효과 범위
* 굵은 빨간 박스 → 실제 추천 표적

이를 통해 숫자 좌표를 직접 찾지 않아도 추천 위치를 시각적으로 확인할 수 있다.

## 13. 데이터 영속성과 동시성

현재 서버는 무상태(stateless) 구조다.

분석한 이미지나 사용자 보드 상태를 데이터베이스에 저장하지 않는다.

처리 흐름은 다음과 같다.

```text
이미지
  ↓
분석 요청
  ↓
Board + Inventory 응답
  ↓
추천 요청
  ↓
Recommendation 응답
```

분석 결과는 클라이언트가 보관하고 다음 추천 요청에 다시 전달한다.

현재 프로그램 자체에는 장기적인 보드 진행 상태를 저장하는 기능이 없다.

Monte Carlo 계산은 반복 횟수가 증가할수록 CPU 사용량과 처리 시간이 증가한다.

## 16. 향후 개선 사항

### 16.1 연속 행동 최적화

현재 추천은 현재 상태에서 수행할 **다음 한 번의 행동**을 최적화한다.

향후에는 여러 행동 이후의 결과까지 고려하는 알고리즘을 추가할 수 있다.

후보 방식:

* Beam Search
* Monte Carlo Tree Search
* Dynamic Programming

### 16.2 비균등 보상 분포

현재 모든 미확인 셀이 동일한 보상 확률을 가진다고 가정한다.

실제 게임에서 특정 위치나 패턴에 따른 보상 생성 규칙이 존재한다는 충분한 데이터가 확보되면 위치별 확률을 다르게 적용할 수 있다.

### 16.3 OCR 개선

현재 아이템 수량은 이미지 템플릿 기반으로 인식한다.

향후 다음과 같은 개선을 고려할 수 있다.

* 다양한 해상도 대응
* UI 스케일 변화 대응
* 숫자 폰트 변화 대응
* 이미지 왜곡 보정
* 학습 기반 숫자 인식

### 16.4 이미지 분석 강건성 개선

현재는 색상 임계값과 격자 구조를 중심으로 분석한다.

향후에는 다음과 같은 입력 변화에 더 강하도록 개선할 수 있다.

* UI 테마 변경
* 해상도 변화
* 색상 보정
* 압축 노이즈
* 일부 화면 잘림
* 아이콘 디자인 변화

### 16.5 단일 요청 분석 API

현재 이미지 분석과 추천은 각각 별도의 API로 구성되어 있다.

```text
POST /api/analyze
POST /api/recommend
```

향후 다음과 같은 통합 API를 추가할 수 있다.

```text
POST /api/optimize
```

이미지를 한 번 업로드하면 분석과 추천을 연속으로 수행하여 최종 결과를 한 번에 반환하도록 구성할 수 있다.

### 16.6 서버측 오버레이 생성

현재 추천 오버레이는 브라우저 Canvas에서 생성한다.

향후 서버에서 직접 PNG 이미지를 생성하는 API를 추가할 수 있다.

```text
POST /api/overlay
```

## 17. 호환성 규칙

향후 구현을 변경할 때 다음 규칙을 유지한다.

* API 필드를 제거하거나 타입을 변경할 경우 API 버전을 올린다.
* 새로운 API 필드는 기존 클라이언트가 무시할 수 있도록 선택 필드 형태로 추가한다.
* 셀 상태 문자열은 다음 값을 유지한다.

```text
unknown
reward_found
no_reward
```

* API 좌표는 계속 0-based를 유지한다.
* 사용자 인터페이스에서만 1-based 좌표로 변환한다.
* 게임 UI에서 아이템 슬롯 순서가 변경되면 OCR 매핑과 문서를 동시에 수정한다.
* 보드 크기별 총 보상 수 규칙이 변경될 경우 보드 모델과 문서를 동시에 수정한다.
* `docs/openapi.yaml`을 HTTP API의 기준 계약으로 유지한다.
